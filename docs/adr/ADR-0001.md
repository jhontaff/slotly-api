# ADR-0001: Modelo de dominio de reservas y estrategia de concurrencia

- **Estado:** Aceptado
- **Fecha:** 2026-11-05
- **Fase:** 1 · Núcleo del dominio y concurrencia

## Contexto

Slotly es una plataforma donde varios negocios (barberías, consultorios, estudios) publican su disponibilidad y sus clientes reservan turnos. El requisito no negociable es que **un mismo recurso nunca quede reservado dos veces en períodos que se solapan**, aunque lleguen peticiones simultáneas, reintentos de red o modificaciones concurrentes sobre la misma reserva.

Restricciones:
- El dominio debe ser independiente de Spring y JPA (arquitectura hexagonal).
- Los servicios tienen duraciones distintas, así que los turnos no son bloques fijos.
- Base de datos: PostgreSQL, con nivel de aislamiento por defecto (`READ COMMITTED`).
- Volumen esperado: negocios pequeños, con baja contención por recurso.

## Decisión

### 1. Modelo de dominio

Agregados, que se referencian entre sí solo por ID:

| Agregado | Responsabilidad |
|---|---|
| `Negocio` | Tenant. Define la zona horaria (`ZoneId`). |
| `Servicio` | Nombre y duración. |
| `Recurso` | Quien atiende. Contiene su horario semanal y sus bloqueos (value objects). |
| `Cliente` | Datos de contacto. |
| `Reserva` | Período, estado, versión e idempotency key. Protege su propio ciclo de vida. |

**La disponibilidad no se persiste.** Es un modelo de lectura calculado: horario del recurso, menos bloqueos, menos reservas no canceladas.

`Periodo` es un intervalo semiabierto `[inicio, fin)` guardado en UTC (`timestamptz`). El horario semanal se expresa en la hora local del negocio y se convierte usando su `ZoneId`.

Todas las tablas llevan `negocio_id` desde el inicio.

### 2. Invariantes y quién las protege

| # | Invariante | Responsable |
|---|---|---|
| 1 | `fin = inicio + duración` (la duración se copia al reservar) | Agregado `Reserva` |
| 2 | Solo se crea en el futuro (con `Clock` inyectado) | Agregado `Reserva` |
| 3 | Transiciones válidas: `CONFIRMADA → CANCELADA \| COMPLETADA \| NO_ASISTIO`; los estados finales no cambian | Agregado `Reserva` |
| 4 | Solo se cancela o reprograma antes de `inicio` | Agregado `Reserva` |
| 5 | El período está dentro del horario del recurso y fuera de sus bloqueos | Caso de uso + lock pesimista sobre `recurso` |
| 6 | Sin solapamiento entre reservas no canceladas del mismo recurso | **Exclusion constraint en PostgreSQL** |
| 7 | Una idempotency key produce una sola reserva | Constraint único |

### 3. Mecanismos de concurrencia

**a) Solapamiento: exclusion constraint (garantía final).**

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE reserva
   ADD CONSTRAINT reserva_sin_solapamiento
   EXCLUDE USING gist (
    recurso_id WITH =,
    tstzrange(inicio, fin, '[)') WITH &&
  )
  WHERE (estado <> 'CANCELADA');
```

- El rango semiabierto `[)` permite reservas consecutivas (10:00–10:30 y 10:30–11:00).
- Una cancelación libera el rango automáticamente.
- El adaptador traduce el error `23P01` a la excepción de dominio `TurnoNoDisponible`, que la API devuelve como HTTP 409.
- El contrato del puerto `ReservaRepository` declara esa excepción, y el adaptador en memoria para tests unitarios debe cumplirlo.

**b) Reintentos: idempotency key.**

- El cliente envía el header `Idempotency-Key`.
- Se guarda en `reserva` con `UNIQUE (negocio_id, cliente_id, idempotency_key)`.
- Si la misma clave llega con el mismo payload, se responde con la reserva existente.
- Si la misma clave llega con otro payload, se responde HTTP 422.

**c) Modificaciones sobre una reserva existente: locking optimista.**

- `Reserva` lleva una columna `version` (`@Version` en la entidad JPA del adaptador, no en el dominio).
- Cancelar, reprogramar y marcar asistencia que choquen entre sí producen un conflicto de versión, que la API devuelve como HTTP 409.
- Reprogramar actualiza el período de la misma fila. El exclusion constraint la compara contra las demás filas, no contra sí misma.

**d) Horario y bloqueos frente a reservas: locking pesimista.**

- Tanto "crear reserva" como "crear bloqueo" o "cambiar horario" toman `SELECT … FOR UPDATE` sobre la fila del `recurso`.
- Así se serializan las operaciones que leen o modifican la agenda de un mismo recurso, y la invariante 5 no se rompe por una carrera.
- La contención queda acotada a un recurso, lo que es aceptable para el volumen esperado.

Todo se ejecuta en `READ COMMITTED` y en una sola transacción por caso de uso.

## Alternativas consideradas

1. **Materializar los slots (tabla `turno` con estado LIBRE/OCUPADO) y reservar con un UPDATE condicional.**
   - Descartada: obliga a usar duraciones fijas, genera filas por adelantado y crea una segunda fuente de verdad que hay que mantener sincronizada con el horario.

2. **Agregado `AgendaDelRecurso` por día, que contenga sus reservas y valide el solapamiento en memoria con `@Version`.**
   - Es la opción más pura en DDD, porque la invariante vive dentro del agregado.
   - Descartada por ahora: el agregado es más pesado, dos reservas distintas del mismo día chocan aunque no se solapen, y las reservas que cruzan la medianoche complican el límite del agregado.
   - Se revisaría si las reglas de agenda crecen (por ejemplo, máximo de reservas por día o descansos obligatorios).

3. **Aislamiento `SERIALIZABLE` con check-then-insert.**
   - PostgreSQL (SSI) detecta la anomalía, pero obliga a reintentar transacciones en toda la app y el error es genérico.
   - Descartada a favor de un constraint explícito y declarativo.

4. **Solo validar en la aplicación (consultar solapamientos y luego insertar).**
   - Descartada: es exactamente la condición de carrera que se quiere evitar.
   - Se implementa primero de forma deliberada, solo para demostrar el fallo con un test.

5. **Lock distribuido (Redis) o advisory locks.**
   - Descartada: añade infraestructura sin necesidad, porque la base de datos ya resuelve el problema.

## Consecuencias

**Positivas**
- La invariante crítica se cumple aunque un caso de uso tenga un bug o alguien escriba directo en la BD.
- Cada mecanismo resuelve un riesgo concreto y distinto, lo que hace el diseño fácil de explicar y de testear.
- El dominio no depende de Spring ni de JPA.

**Negativas y riesgos aceptados**
- La invariante más importante vive en la infraestructura y no en el agregado. Se mitiga con el contrato explícito del puerto y con tests de contrato que corren contra ambos adaptadores.
- Hay dependencia de PostgreSQL (`btree_gist`, exclusion constraints). Es aceptable: no se planea cambiar de motor.
- El modelo asume capacidad 1 por recurso. Las clases grupales con cupo necesitarían otro mecanismo (contador con lock o UPDATE condicional) y su propio ADR.

## Verificación

Tests de integración con Testcontainers (PostgreSQL real):

1. **Carrera por el mismo turno.** N hilos (por ejemplo 20) arrancan a la vez con un `CountDownLatch` y reservan el mismo período. Debe haber exactamente 1 éxito, N−1 `TurnoNoDisponible` y 1 fila en la BD.
2. **Solapamiento parcial.** 10:00–10:45 contra 10:30–11:00: la segunda reserva se rechaza. 10:00–10:30 contra 10:30–11:00: ambas se aceptan.
3. **Idempotencia concurrente.** N peticiones con la misma clave: 1 reserva, y todas las respuestas con el mismo ID.
4. **Conflicto de versión.** Cancelar y reprogramar la misma reserva en paralelo: una tiene éxito y la otra recibe 409.
5. **Bloqueo frente a reserva.** Crear un bloqueo y una reserva en el mismo rango en paralelo: nunca quedan ambos.
6. **Cancelación libera.** Después de cancelar, el mismo período se puede volver a reservar.

Orden de implementación sugerido: primero el test 1 contra la versión ingenua (debe fallar), luego el constraint (debe pasar). Ese antes y después se documenta en el README.
